## 1. Context
`ARCHITECTURE.md` §3.1 originally fixed the grid cell at 3:5 (width:height = 0.60). Fira Code's natural monospace cell is 1:2 (advance 1200, ascender 1800, descender −600, line gap 0, upem 1950). Filling a 3:5 cell therefore forced anisotropic glyph scaling: `GLYPH_WIDEN = 1.10` on top of a non-uniform vertical scale, giving wide, vertically compressed text. M2.1–M2.15 were built on 3:5 (24 × 40 px cells in the code).

The same amendment (M2.16) also fixes two related problems: the original 3:5 logo allocations (5 × 3 and 3 × 2) and the UI scale values planned for the View menu (50 / 75 / 100 / 125 / 150 %) do not map to whole cells of any single integer geometry.

## 2. Options Considered
* **Option A:** Keep 3:5 and the anisotropic glyph scale. (Pros: no change. Cons: distorted text, per-glyph tuning, box-drawing joins depend on the widening hack.)
* **Option B:** Keep 3:5 and add per-character correction or inter-character spacing. (Pros: hides the symptoms. Cons: breaks the monospace grid contract and adds per-glyph special cases.)
* **Option C:** 1:2 cells, the font's natural ratio. (Pros: zero distortion. Cons: the line box fills the whole cell with zero leading, so ink from adjacent rows touches, and the product design asked for 4:9.)
* **Option D:** Exactly 4:9 cells, `W = 4k`, `H = 9k`, with one uniform glyph scale `s = W / advance` and natural proportions. (Pros: no distortion; `L = 8k ≤ H = 9k` leaves `k` px of leading; all metrics are exact integers for every `k`; Unicode box-drawing joins using the font's own glyphs; near-square logo blocks of 7 × 3 and 4 × 2 cells. Cons: every ratio-dependent artefact must be redone once.)

## 3. Decision
We select **Option D**.
* **D1 (cell):** `W = 4k`, `H = 9k` physical pixels for one positive integer `k`; ratio exactly 4:9; default `k = 5` (20 × 45 px). Permitted values: 2, 3, 4, 5, 6, 7 (`k = 2`, 8 × 18 px, added by the second amendment).
* **D2 (glyphs):** one uniform scale `s = W / advance` (`= k / 300` for Fira Code), natural proportions. No horizontal stretching, no spacing, no per-character factors, no GPU resampling of glyph rasters. Box drawing uses the font's own continuous strokes (verified for `k` = 2…7).
* **D3 (UI Scale, amended 2026-10-26 by D14):** UI Scale presents exactly four labels: 80%, 100% (default), 120% and 140%. These labels map by index to the existing rendering multipliers `scale_factor_percent` 60%, 80%, 100% and 120%, respectively. Thus the default visible 100% uses the former 80% rendering size. The former 140% rendering multiplier is removed; no 60% label is offered. The selected label is per-window user state; its multiplier is mapped from the fixed table. `monitor_reference_scale` and `effective_k` remain derived per-window state (`ARCHITECTURE.md` §§3.1.1, 4.2). The existing integer monitor derivation and 4:9 cell geometry are unchanged.
* **D4 (minimum grid):** the window is never smaller than 82 × 30 cells at any scale (`328k × 270k` physical px, `656 × 540` at `k = 2`); the composed grid is never smaller, and a surface that is too small is cropped, not reshaped. Scales that cannot fit are clamped (never skipped in the control, D13); the ratio and the minimum grid are never violated silently (`ARCHITECTURE.md` §3.1.1). `Interface_Exemple.txt` stays an 82 × 28 reference; the extra two rows of the minimum belong to the flexible central body.
* **D4a (window fit, limitations):** `winit` exposes the monitor size but not the OS work area, so windowed mode uses the conservative estimate `usable_height = h − h/16` (taken from the top edge for positioning), `k_fit = min(⌊w/328⌋, ⌊usable_height/270⌋)`. This is an estimate, not a guarantee: the actual window size and position are verified after every change and asynchronous resizes are expected, and the monitor size is never assumed to equal the available area. Fullscreen uses the full monitor and is refused if `k = 2` cannot fit (below 656 × 540 px). An unknown monitor uses reference 5 and is re-derived when information arrives. If even `k = 2` does not fit, the exact 4:9 grid and the 82 × 30 minimum are preserved, the limitation is logged once, and the ratio is never changed silently. `drag_resize_window` is `NotSupported` on macOS (`winit` 0.30.13); the frameless window stays manually resizable through the application-managed resize of D10.
* **D5 (logos):** major tools 7 × 3 cells, minor tools 4 × 2 cells. The 3:5 allocations (5 × 3, 3 × 2) are superseded. The 256 × 256 atlas slice and 240 × 240 drawn logo rules (§3.2) are unchanged. Logos are the single permitted resampled content (always downscaled by the shader with a filtered sampler); text glyphs are never resampled (`ARCHITECTURE.md` §3.3).
* **D6 (HiDPI):** OS display scaling never scales the grid. All geometry is in physical pixels and every size passed to `winit` is an explicit `PhysicalSize`; the size actually applied is read back and never assumed; size is chosen only by the UI Scale preference together with the monitor's pixel dimensions (D13); `scale_factor` is never an input, and a macOS display-scale change acts only through the new monitor pixel size it produces.
* **D7 (UI palette and themes, amended by ADR 0006):** each window starts Dark with Color unchecked. Unchecked is exactly white `#FFFFFF` on black `#000000` in Dark, black on white in Light, with the existing glyph layout. Checked Dark uses background `#071521`, Text `#FFFFFF`, Contour `#41B4E5`, Action `#FFA24A`; checked Light uses background `#FFFFFF`, Text `#111827`, Contour `#0969A0`, Action `#9A4D00`. Theme and Color are independent manual per-window choices. Component semantics assign one Text/Contour/Action role per cell; hover and interaction states cannot change roles or palette entries. Coverage-based glyph antialiasing is permitted; decorative colour, gradients, shadows, glow, brightness multipliers and widget inversion remain forbidden. Same-cell single-stroke contour mapping, shared-cell ownership, logo sampling/ink and viewport clear follow `ARCHITECTURE.md` §§3.2–3.6 and ADR 0006. No model display-style change is authorized.
* **D8 (ASCII hover, no invented state markers):** M2.16 removed colour-based hover; the already approved M2.25 exception in `ARCHITECTURE.md` §3.5 permits only instantaneous Unicode border substitutions and one Controller-owned hovered target. Each substituted cell keeps its semantic ink role (ADR 0006); no hover colour change, brightness, animation or shader effect is permitted. Other states draw only documented ASCII structures; invented `>`/`<` markers and widget inversion remain rejected. The M2.7 active-segment separator deviation was limited to M2.21. The M2.23 editing caret `▏` uses Text ink, appears only during editing, and needs no second draw call or caret-specific shader data.
* **D9 (per-window state, amended by ADR 0006 and D14):** the selected UI Scale label, its mapped `scale_factor_percent`, `monitor_reference_scale`, `effective_k`, Theme and Color are window-local state (`ARCHITECTURE.md` §4.2). Every new window starts with label 100% (factor 80%), Dark and Color unchecked; it inherits none of these from another window or OS appearance. The label is user state, the multiplier is derived from its fixed preset mapping, monitor reference and `effective_k` are recomputed for the window. Theme/Color remain independent per-window presentation choices.
* **D10 (frameless resize):** the window has no native decorations and MUST stay manually resizable. Native `drag_resize_window` is tried first; on `NotSupported` the Controller runs an application-managed resize using only safe `winit` 0.30 API (pointer events, `outer_position`, `request_inner_size`, `set_outer_position`): snapshot on press, target re-derived from the snapshot and the screen-space pointer on each move, whole cells, minimum 82 × 30, size requested before position, cancelled on release or focus loss, never overriding a control (`ARCHITECTURE.md` §3.1.1, `README_UI.md` §25.1). East, south and south-east are robust; west/north zones need two non-atomic calls and are a reported limitation verified manually in M2.17. No `unsafe`, no platform workaround.
* **D11 (glyph atlas):** the glyph atlas is deterministic: the required set (printable ASCII, every character of `docs/ui_design/*.txt`, `▏`) is rasterised once per `k` at the integer-`k` uniform scale and never modified; any other character is drawn as `?`; no on-demand rasterisation. Filtered sampling is permitted for logo textures only; glyphs keep the nearest-neighbour contract (D5).
* **D13 (automatic per-monitor adaptation, added 2026-10-16):** `effective_k` is a pure integer function of (monitor physical size, windowed/fullscreen mode, `scale_factor_percent`) and of nothing else. `k_fit(mode) = min(⌊w/328⌋, ⌊avail_h/270⌋)` (`avail_h = h − h/16` windowed, `h` fullscreen); `monitor_reference_scale = max(k_fit(windowed) − 1, 2)` if `k_fit(windowed) ≤ 3` (the compact class, always 2), else `min(k_fit(windowed), 5)` (second amendment; before it, `clamp(k_fit(windowed), 3, 5)`); `k_req = (reference × scale_factor_percent + 50) / 100` (round half up; no tie can occur because every rendering factor is a multiple of 20); `effective_k = clamp(k_req, 2, clamp(k_fit(mode), 2, 7))`. The compact class is identified by pixels only (`k_fit(windowed) ≤ 3`: usable height 810…1079 px, width ≥ 984, which includes Full HD); no monitor name, model or vendor is ever hard-coded. The ratio 4:9, `W = 4k`, `H = 9k`, natural Fira Code proportions, integer pixels, the 82 × 30 minimum, O(1) hit-testing and the single UI draw call are unchanged. Re-derivation happens only at start-up, on a monitor change, a monitor resolution change, a macOS display-scale change, a fullscreen enter/exit and a preference change. The change is applied by one atomic transition (prepare everything, abandon as a whole on failure, then commit metrics, glyph atlas, `CellGrid`, GPU buffers, minimum window size and pointer mapping as one published value; the atlas is rebuilt only when `k` changes). Oscillation is excluded by construction: window size and position are outputs, never inputs; echoes of the transition's own `Resized`/`Moved`/`ScaleFactorChanged` events never start a transition; a monitor change during a window drag is applied once after 150 ms without movement; at most one corrective window request per input tuple. Moving to a smaller monitor keeps the user's desired grid (restored on return), clamps it to whole cells inside the usable rectangle (never below 82 × 30) and shifts the window the minimum distance so its whole rectangle lies inside the usable rectangle; the frameless MenuBar row therefore stays reachable. **A small monitor may map several labels to the same `effective_k`** (1920×1080 windowed: labels 80/100/120/140% give `k` = 2/2/2/2; 2560×1664: labels 120/140% give `k = 5`); this is intended and documented, the control never skips or hides a label, and a label change that does not change `k` runs no transition. Full rules: `ARCHITECTURE.md` §3.1.1.
* **D12 (status bar, caret, rename):** the StatusBar frame-rate segment is a fixed 7-cell, 3-digit right-aligned field saturating at 999 (M2.24); `▏` is the editing caret (D8, M2.23); `Rename` opens on double-click (M2.20).

## 4. Consequences
* **Positive:** Undistorted text; one geometry source of truth; deterministic integer metrics at every scale; fewer special cases in the atlas builder and shader.
* **Positive:** The UI scale is an integer and cheap: the glyph atlas depends only on `k`, the theme does not touch it.
* **Negative / Risks:** The code and snapshot tests from M2.1–M2.15 assume 24 × 40 and `GLYPH_WIDEN`; they are rewritten in M2.16. Completed milestones M2.1–M2.15 are not edited; the plan records them as historical.
* **Negative / Risks:** At `k = 5` the minimum 82 × 30 grid is 1640 × 1350 physical px, which does not fit a 1920 × 1080 monitor; `k = 4` would fill it exactly (1312 × 1080) and leave no room for OS chrome, so the estimate gives `k_fit = 3` there. The per-monitor derivation in `ARCHITECTURE.md` §3.1.1 handles this: after the second amendment 100 % gives `k = 2`, 8 × 18 px (minimum window 656 × 540, about half the usable height), one step below the fit.
* **Negative / Risks:** `winit` 0.30 exposes the monitor size but not the OS work area, and `unsafe` is forbidden, so the fit test is the `h/16` reserve estimate and can be wrong in either direction; a window may overlap OS chrome or be smaller than necessary. M2.17 logs, verifies and repositions (one corrective request at most).
* **Negative / Risks:** On macOS `drag_resize_window` is unavailable, so edge resizing is application-managed (D10). `winit` offers no atomic move-and-resize, so the west/north zones may show jitter; this is verified manually in M2.17 and reported, never patched with `unsafe`.
* **Positive (per-monitor):** One preference gives a comparable, usable UI on a Retina laptop and on an external 1080p monitor; a window that was too large for the monitor can no longer arise from the scale choice alone, and the preference survives monitor changes.
* **Negative / Risks (per-monitor):** The monitor is only known by its pixel size, so "100 %" on a monitor is a pixel-count heuristic, not a physical size (no DPI or millimetre data is used). Small monitors collapse several percentages to one `k`. A monitor change during a drag is applied up to 150 ms late. `winit` 0.30 has no monitor-change event, so the Controller compares a monitor snapshot on window events and at most every 500 ms. Mixed-scale multi-monitor coordinates in `winit` can disagree by a pixel or by a monitor's scale; the read-back and the single corrective request bound the effect. These are verified manually in M2.17 on the MacBook Air Retina display and an external 1920×1080 monitor.
* **Rejected alternatives (per-monitor):** (a) using `scale_factor`/DPI to choose `k`: breaks D6 and is unreliable across macOS scaled modes; (b) fractional `k`: breaks integer cells; (c) one-shot start-up choice (the earlier D3): does not survive a monitor change; (d) re-deriving from the current window size: couples `k` to its own output and oscillates; (e) skipping unavailable percentages in the control: hides the preference and contradicts "preference unchanged across monitors".
* **Mitigation:** M2.16 tests the metrics and box-drawing continuity for all six `k` (2…7) even though only `k = 5` is used at runtime. If a future font fails continuity at any `k`, a procedural box-drawing rasteriser needs a new approval.
* **Note:** `docs/adr/0001-*.md` and `docs/adr/0002-*.md` are not modified.

## 5. Second amendment (2026-10-16): `k = 2` for the compact class
**Decision (human, applied by the Architect):** on Full HD displays the effective 100 % is one step smaller, `k = 3 → k = 2` (8 × 18 px). MacBook Retina 100 % stays `k = 5` (20 × 45 px). The user-facing preference stays 100 % on both. The 4:9 ratio is exact at `k = 2` (`W = 4k = 8`, `H = 9k = 18`). The permitted range becomes 2…7; the minimum window at `k = 2` is `656 × 540`; scale clamping is `[2, k_cap]` with `k_cap = clamp(k_fit(mode), 2, 7)`; the no-fit and fullscreen-refusal thresholds move from `k = 3` to `k = 2`. No monitor name is hard-coded: the compact class is `k_fit(windowed) ≤ 3`. Fira Code was checked at `k = 2` (numeric and coverage check, `ARCHITECTURE.md` §3.1, *Fira Code at `k = 2`*): metrics `L = 16`, `top = 1`, `baseline_y = 13`; all required glyphs rasterise and stay pairwise distinct; box-drawing joins are edge-identical; strokes are thin (about 1.07 px) and anti-aliased.

**Behaviour change table** (historical 2026-10-16 preference ladder; current labels and factors are defined by D14 and `ARCHITECTURE.md` §3.1.1):

| Monitor | Before | After |
|---|---|---|
| 1920 × 1080 | 3 / 3 / 3 / 3 / 3 | 2 / 2 / 2 / 2 / 3 |
| 1366 × 768 | 3 / 3 / 3 / 3 / 3 (overflow) | 2 / 2 / 2 / 2 / 2 (fits) |
| 1920 × 1200 | 3 / 3 / 4 / 4 / 4 | 2 / 3 / 4 / 4 / 4 |
| 2560 × 1664 and larger | unchanged | unchanged |

**Rejected alternatives (second amendment):** (a) a Full HD special case by name or resolution string (violates the no-hard-coding rule; the pixel class covers it); (b) lowering every reference by one (changes the MacBook, which must stay `k = 5`); (c) a sixth preference value (violates "exactly five").

### Open compatibility points (not decided here; for the human)
1. **Historical coarse ladder at reference 2 (superseded by D14).** The former five-multiplier ladder had several duplicate values on Full HD. D14 replaces that ladder with four visible labels mapped to factors 60/80/100/120; on Full HD all four remain `k = 2` under the existing minimum and fit constraints.
2. **Cliff between classes.** The reference jumps 2 → 4 between `k_fit(windowed)` 3 and 4 (1920 × 1080 → 1920 × 1200 doubles the 100 % cell: 8 × 18 → 16 × 36). Before the amendment the jump was 3 → 4. Extending the one-step reduction to `k_fit = 4` (1920 × 1200 → 3) would smooth it but changes monitors the human did not name.
3. **Legibility is unverified on screen.** The `k = 2` check is numeric (rasteriser run in a scratch program, coverage dumps), not visual. Stems and box lines are about 1.1 px, anti-aliased, at 20–87 % coverage; `.`/`,`, `:`/`;`, `` ` ``/`'` differ by about 3 px of coverage. A human check on a real 1920 × 1080 monitor is required at M2.17 (added to the manual checklist, `README_UI.md` §25.1).
4. **Resize ring.** The ring is one cell wide (8 × 18 px at `k = 2`), a small pointer target; the cell-based rule (`README_UI.md` §25.1) is kept.
5. **Logos.** At `k = 2` the minor logo (32 × 32 px) is a 7.5:1 minification with a bilinear sampler and no mipmaps (`ARCHITECTURE.md` §3.3); aliasing is accepted but must be re-judged by the first logo milestone, which may need a mip chain.
6. **Superseded code and tests.** The implementation in the working tree (uncommitted `crates/newell-ui/src/window.rs`: `MIN_K = 3`, `monitor_reference_scale = clamp(k_fit, 3, 5)`, `effective_scale`; `crates/newell-app/src/scale.rs` and its tests; glyph-atlas and metrics tests over `k` 3…7) assumes `k` 3…7 and `k = 3` for 1080p. It is not modified by this amendment and must be updated by the Executor from `docs/plans/M2-ui-framework.md` (M2.16 range, M2.17 derivation and tests).

## 6. Third amendment (2026-10-26): displayed UI Scale labels

**D14 (human-requested):** the View menu displays 80%, 100%, 120% and 140%,
with the exact mapping 80→factor 60, 100→factor 80, 120→factor 100 and
140→factor 120. The old factor-140 preset is removed. The 100% label is the
startup default and uses the old factor-80 rendering size. The monitor formula,
cell geometry, atlas generation and window fit are unchanged. No optional 60%
label is added: its proposed factor 40% requests `k = 1` at reference scale 2
and is clamped to the existing minimum `k = 2`, duplicating other choices.
